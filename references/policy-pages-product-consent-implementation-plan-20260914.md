# 휴심컬러 Toss 심사 대비 정책 페이지·동의 흐름 구현 제안

> **법률·개인정보 전문 검토 전 설계안입니다.** 본 문서는 현재 코드와 운영 설계를 기준으로 정책 페이지의 범위·데이터 연결·확정 필요 정보를 정리한 것입니다. 이용약관, 개인정보처리방침, 환불·취소정책의 최종 문구 및 실제 적용 여부는 전자상거래·개인정보보호 전문 검토 후 확정해야 합니다.

## 1. 현재 구조를 기준으로 한 정책 적용 범위

휴심컬러의 정책은 무료 체험과 유료 분석, 향후 코칭을 하나의 문서 체계로 관리하되, 상품군별 제공 방식과 환불 기준은 분리해야 한다. 현재 공통 카탈로그에는 무료 컬러 체험, 개인 심화분석, 부부·연인 관계 심화분석, 부모·자녀 관계 심화분석, 친구 관계 분석, 1:1 개인 코칭, 부부·커플 코칭, 기타 관계 코칭이 정의되어 있다. 분석 상품과 코칭 상품은 모두 상품·가격 버전·주문·쿠폰·결제거래를 공유하지만, 분석은 구매권한과 검사 시작·결과·PDF로, 코칭은 전액 결제 뒤 일정 대기·일정 확정·완료·취소·노쇼로 이행된다.

| 상품군 | 현재 상태 | 정책 문서에서 분리해 고지할 내용 | 결제·운영 연결점 |
|---|---|---|---|
| 무료 컬러 체험 | 공개 이용 가능 | 무료 제공 범위, 결과의 참고적 성격, 서비스 성격·한계 | 무료 접근·결과 표시 |
| 친구 관계 분석 | 공개 이용 가능 | 무료 제공 범위, 두 사람 입력 시 유의사항 | 관계 검사·공유 |
| 개인 심화분석 29,000원 | 일반 공개 결제 차단 | 가격, 제공 단계, 검사 시작 시점, 결과/PDF, 취소·환불 기준 | `personal_deep`, entitlement, analysis run |
| 부부·연인 59,000원 | 일반 공개 결제 차단 | 두 사람 정보 처리, 제공 단계, 결과/PDF, 취소·환불 기준 | `couple_love_deep`, entitlement, analysis run |
| 부모·자녀 39,000원 | 일반 공개 결제 차단 | 보호자·두 사람 정보 처리, 결과/PDF, 취소·환불 기준 | `parent_child_deep`, entitlement, analysis run |
| 1:1 프리미엄 컬러심리 코칭 | 판매 UI 미구현 | 전액 결제, 상담 방식·기간, 일정 확정, 변경·취소·노쇼 | `personal_coaching`, booking |
| 부부·커플 관계 코칭 | 판매 UI 미구현 | 두 사람 정보·상담 방식, 일정 확정, 변경·취소·노쇼 | `couple_coaching`, booking |
| 기타 관계 코칭 | 카탈로그만 존재 | 가격·대상·제공 범위 확정 후 정책 반영 | `relationship_coaching`, inactive |

현재 Production에서는 일반 고객의 유료 분석 결제·검사 진입이 정책 게이트로 차단돼 있다. 정책 페이지 구현은 이 공개 차단 상태를 변경하지 않으며, 코칭 판매 UI도 이번 제안의 범위에 포함하지 않는다.

## 2. 이용약관 설계안

이용약관은 서비스별 설명을 길게 반복하기보다 공통 계약 구조를 정하고, 상품 상세·환불정책으로 연결하는 방식이 적절하다. 다음 조항을 기본 골격으로 권장한다.

| 조항 | 필수 내용 | 현재 시스템과의 연결 |
|---|---|---|
| 목적·정의 | 회원, 비회원, 주문, 결제, 이용권, 분석, 코칭 예약의 정의 | 공통 `user_id`, customer, order, entitlement, booking |
| 서비스 범위 | 무료 체험, 분석, 향후 코칭의 제공 범위와 개별 상품 페이지 우선 원칙 | 상품 카탈로그·가격 스냅샷 |
| 이용자 정보·책임 | 정확한 정보 입력, 타인의 정보 입력 시 적법한 권한, 계정·이메일 관리 | 비회원 이메일·관계 검사 입력 |
| 서비스 성격과 한계 | 결과는 자기이해·관계 성찰을 위한 참고 정보이며 의료·심리치료·진단을 대체하지 않음을 고지 | 분석 결과 본문은 변경하지 않고 정책·상품 안내에서 고지 |
| 주문·결제 | 표시가격, 쿠폰, 서버 승인 기준, 결제 실패·취소·중복 처리 | orders, payment_transactions, coupon_redemptions |
| 분석 제공 개시 | 결제만으로 결과 접근이 열리지 않고 서버 구매권한과 검사 시작 기록을 기준으로 제공됨을 설명 | entitlement, analysis_runs.startedAt |
| 코칭 예약 | 전액 결제 후 일정 대기, 운영자 일정 확정, 온라인/대면 방식, 변경 요청 | coaching_bookings, booking events |
| 지식재산·금지행위 | 결과·PDF·공유물의 이용 범위와 부정 이용 금지 | private document, immutable share snapshot |
| 서비스 변경·중단·분쟁 | 사전 고지 원칙, 장애 처리, 고객문의, 정책 적용 버전 | 정책 버전·감사 로그 |

분석 및 코칭별 가격·제공기간·예약 규칙은 약관 본문에 고정하기보다 상품 페이지와 환불·취소정책에서 명확하게 제시하고, 약관은 해당 페이지의 정책 버전과 연결해야 한다. 가격은 DB의 활성 가격 버전이 진실의 원천이므로 화면 상수만으로 고지하지 않는다.

## 3. 개인정보처리방침 설계안

개인정보처리방침은 현재 입력 화면과 서버의 암호화·해시 처리, PDF·이메일 outbox, 계정 연결, 예약 메모의 실제 흐름을 반영해야 한다. 특히 현재 개인 심화와 관계 정보 입력에는 나이, 직업, 성별, 신앙/종교, 고민 분야, 관계 관련 정보가 포함될 수 있다. 신앙/종교 관련 값은 민감정보에 해당할 가능성이 있으므로, 수집 필요성·선택 입력 전환·별도 동의·접근 통제를 전문 검토로 확정해야 한다.[3]

| 처리 목적 | 현재 또는 예정 수집 항목 | 보관·보호 구현 상태 | 정책 문서·동의 화면에서 확정할 점 |
|---|---|---|---|
| 회원·비회원 주문 식별 | 이메일, OAuth 식별자 | 이메일 HMAC·암호화, user/customer 연결 | 필수/선택 구분, 비회원 계정 연결 인증 절차 |
| 결제·쿠폰·환불 | 주문번호, 결제 상태·금액, 쿠폰 사용 상태 | 주문·거래·쿠폰 원장 | 법정 보존 검토와 일반 서비스 데이터 보관 분리 |
| 분석 제공 | 나이, 직업, 성별, 신앙/종교, 고민 분야, 색상·심리카드 선택, 관계 입력 | analysis run·결과·PDF 흐름, 일부 입력은 기기 로컬 저장 | 각 항목 필요성, 민감정보 별도 동의, 동의 거부 시 서비스 범위 |
| 결과·PDF 전달 | 결과 참조, PDF, 이메일 | private storage, 문서 보관기한, 이메일 outbox 재시도 | 회원 1년·비회원 7일 설계와 파기·다운로드 가능 기간의 정확한 고지 |
| 코칭 예약 운영 | 일정 희망, 온라인/대면 방식, 예약 메모 | 예약 세부사항·운영 메모 암호화 | 필수 항목, 상담 관련 추가 정보 수집 시 별도 고지 |
| 고객 지원·후기 | 문의 내용, 후기 닉네임·내용 | 현행 후기·관리자 구조 | 고객지원 보유기간, 후기 공개·삭제 기준 |

정책에는 개인정보처리자, 개인정보 보호책임자, 수집·이용 목적, 보유·파기, 처리위탁 또는 제3자 제공, 해외 이전 해당 여부, 권리 행사 방법, 안전성 확보조치, 쿠키·접속기록 처리, 고충 처리 연락처, 처리방침 변경 이력을 실제 사실에 맞게 넣어야 한다. 결제, 이메일, 인증, 호스팅·DB·파일 저장 서비스는 계약·데이터 경로를 확인한 뒤 **위탁인지 제3자 제공인지 구분**해 기재한다. 확인 전 특정 사업자나 저장 위치를 추정해 정책에 적지 않는다.

## 4. 환불·취소정책 설계안

디지털 분석과 코칭 예약은 동일 정책으로 처리하면 안 된다. 아래는 현재 승인된 운영 설계를 정책 문서와 서버 상태 전이에 연결하기 위한 초안이다.

| 구분 | 고객에게 고지할 기준 초안 | 서버·운영 기준 | 최종 확정 전 검토 항목 |
|---|---|---|---|
| 결제 전·결제 실패·사용자 취소 | 결제 승인 전 또는 미승인 주문은 서비스가 시작되지 않으며 결제가 완료되지 않음 | pending/failed/cancelled order, coupon release | PG 표시 문구와 실제 상태 일치 |
| 디지털 분석 시작 전 | 결제 승인 뒤에도 **첫 컬러 선택이 서버에 검사 시작으로 기록되기 전**에는 전액 환불 요청 가능 | entitlement active, analysis run 미생성 | 전자상거래상 제공 개시 고지·별도 동의 방식 |
| 디지털 분석 시작 후 | 제공 개시 이후의 청약철회 제한 가능성, 오류·중복결제·미제공 시 별도 구제 절차 고지 | analysis run started/completed, 결과·PDF 상태 | 제한 요건, 예외·환급 기간을 법률 검토로 확정 |
| PDF·이메일 장애 | 결과/PDF 생성·이메일 발송 실패는 재생성·재발송 우선, 해결 불가 시 환불 검토 | private_documents, email_outbox, 운영자 재시도 | 재시도 회수·처리 기한·보상 기준 |
| 코칭 예약 변경·취소 | 기존 운영안인 예약 전날 23:59:59 KST까지 전액 취소는 정책 후보로 유지 | booking status·cancelledAt·reason | 확정일, 당일 취소·노쇼, 일정 변경·사업자 취소 예외 |
| 코칭 노쇼 | 기본 환불 제한 후보이나 고객 고지·예외·분쟁 기준을 명확히 기재 | no_show status·운영 감사 이력 | 소비자분쟁해결기준·개별 사정 반영 |

일반 전자상거래의 청약철회와 디지털콘텐츠·용역 제공 개시 예외는 고객에게 알기 쉬운 방식으로 고지되어야 하며, 환급·취소 처리 기한은 관련 법령·결제수단 절차를 포함해 최종 검토해야 한다.[2] 정책 문구와 서버의 `analysis_runs.startedAt`, 주문의 refunded/cancelled 상태, PG 취소 결과가 서로 달라지지 않도록 구현해야 한다.

## 5. 권장 동의·고지 흐름

정책 페이지 링크만으로는 주문 시점의 계약·동의 증빙이 부족할 수 있다. 모든 동의는 기본 체크 해제, 필수와 선택 분리, 버전·시각·주문 연계를 원칙으로 설계한다.

| 화면 | 필수 고지·동의 | 선택 동의 | 저장할 운영 기록 |
|---|---|---|---|
| 공개 푸터·상품 상세 | 사업자정보, 가격, 제공 방식, 정책 3종 링크 | 없음 | 정책 공개 버전 |
| 비회원 주문서 | 이용약관 동의, 개인정보 수집·이용 동의, 환불·취소정책 확인 | 마케팅 수신 동의 | 정책 문서 ID·버전·동의 시각·주문번호 |
| 분석 시작 직전 | 디지털 분석 제공 개시 시점과 환불 제한 가능성의 명확한 확인 | 신앙/종교 등 민감정보 처리 별도 동의가 필요하다고 확정될 경우 별도 체크 | 제공 개시 고지 버전·동의 시각·analysis run ID |
| 코칭 예약 정보 | 예약·변경·취소·노쇼 정책 확인, 필수 예약 정보 수집 동의 | 상담 메모·추가 정보 처리 동의가 필요할 경우 분리 | 예약 정책 버전·동의 시각·booking ID |
| 회원가입·이메일 연결 | 계정 이용약관·개인정보 동의 | 마케팅 | user ID·정책 버전·동의 시각 |

`orders.policyVersion`은 현재 기본값 `pending_legal_review`만 보관하므로, 실제 정책 구현 단계에서는 문서별 버전과 필수·선택 동의의 시각을 별도 append-only 동의 이력으로 저장하는 구조를 권장한다. 주문 하나에 이용약관, 개인정보, 환불정책, 제공 개시, 민감정보 처리 동의가 서로 다른 버전으로 적용될 수 있기 때문이다.

## 6. 필요한 DB·API·화면 변경안

정책이 법률 검토로 확정된 뒤에만 아래를 구현한다. 지금은 설계 제안이며, 코드·DB·공개 정책은 변경하지 않는다.

| 계층 | 권장 변경 | 목적 |
|---|---|---|
| DB | `policy_documents`(문서 유형, 버전, 제목, 본문, 시행일, 상태) | 확정·게시·폐기 문서의 버전 관리 |
| DB | `policy_consents`(user/customer/order/analysisRun/booking, 문서 ID·버전, 동의 유형, 필수 여부, 시각, IP/UA 최소 기록 검토) | 주문·제공 개시·예약 동의 증빙 |
| DB | `refund_requests` 또는 `refund_events`(요청·승인·거절·PG 취소·사유·시각) | 환불 요청과 실제 Toss 취소를 분리 추적 |
| API | 공개 정책 조회, 주문·분석·예약 동의 기록, 관리자 정책 버전 관리, 환불 운영 API | UI·주문·관리자 연결 |

## 8. 권장 구현 순서

1. 위 미확정 정보를 사업자·운영·법률 검토로 확정한다.
2. 세 정책의 초안을 문서 버전·시행일과 함께 검토·승인한다.
3. 정책 공개 페이지와 공통 푸터 링크를 구현하되, 결제 공개 gate는 계속 닫아 둔다.
4. 주문·분석 시작·예약 화면에 필수/선택 동의와 append-only 동의 이력을 구현한다.
5. 환불 요청·운영 승인·Toss 취소·예약 취소를 하나의 관리자 감사 흐름으로 연결한다.
6. 정책 링크, 동의 저장, 오류·취소·재시도, 모바일 브라우저를 검증한 뒤 Toss 심사·실결제 QA를 별도 진행한다.

## 9. 소그룹 세미나 공개 노출 점검

현재 프로젝트의 공개 화면·컴포넌트·서버·공통 카탈로그와 저장 이력에서 `소그룹`, `세미나`, `seminar`, `group coaching` 노출 구현을 찾지 못했다. 현재 Production 공개 첫 화면도 무료 컬러 체험, 개인 심화분석, 관계 분석만 표시한다. 따라서 데이터를 삭제하거나 코드를 제거할 필요 없이, 현 상태가 이미 “홈페이지 노출 비활성화” 요구를 충족한다. 향후 코칭 판매 UI는 1:1 프리미엄 컬러심리 코칭과 부부·커플 관계 코칭을 중심으로 구성하고, 기타 관계 코칭은 비활성 카탈로그로 유지한다.
