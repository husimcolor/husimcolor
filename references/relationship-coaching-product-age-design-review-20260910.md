# 관계코칭 상품 분리 및 부모·자녀 연령 정보 설계 검토

> **검토 범위:** 현재 구현된 코드와 데이터 구조만 검토했습니다. 분석 문장, 결과 UI, 결제 로직, 부모·자녀 코칭 구조 및 Production 배포에는 변경을 가하지 않았습니다.

## 결론 요약

관계코칭을 **부부·연인 유료**, **부모·자녀 유료**, **기타 관계 무료**의 세 상품으로 나누는 방향은 적절합니다. 다만 현재는 모든 관계가 하나의 `/couple-start` 진입·공통 세션으로 시작하고, 결제 권한도 `premiumUnlocked`라는 단일 기기 저장값으로 처리됩니다. 그러므로 화면 카드만 세 개로 나누기보다, **상품 식별자·권한·결과 스냅샷을 함께 분리**해야 가격과 결과 범위가 섞이지 않습니다.

부모·자녀 분석에는 연령 정보가 의미 있는 변수입니다. 그러나 정확한 숫자 나이보다 **자녀의 발달·생활 단계**를 우선 선택하고, 부모 연령대는 보조 맥락으로 받는 방식이 현재 분석 구조와 개인정보 최소화 원칙에 더 잘 맞습니다.

## 1. 현재 구조에서 확인한 점

| 영역 | 현재 상태 | 설계상 의미 |
|---|---|---|
| 홈 진입 | 홈의 단일 `커플 세션` 버튼이 `/couple-start`로 이동합니다. | 상품 선택 이전에는 관계 상품의 가격·범위가 분리되어 있지 않습니다. |
| 검사 세션 | `CoupleSessionData`에는 관계 유형, A/B 성별·종교·컬러·카드·공유 ID만 저장됩니다. | 상품 ID, 구매 상태, 연령·발달 단계가 없습니다. |
| 검사 단계 | 두 사람의 컬러 3개·심리카드 3개 선택은 공통 흐름입니다. | 입력 UI와 개인 분석 엔진은 재사용하기 좋습니다. |
| 결제 | 현재 결제 화면은 개인 심층 해석과 커플 상품을 한 배열로 두고, 입금 기록에는 금액만 저장합니다. | `59,000원`과 `39,000원` 상품을 금액으로만 구분하면 운영·권한 관리가 취약합니다. |
| 권한 | `premiumUnlocked`와 무료체험 시작 시각이 전역 AsyncStorage 키로 처리됩니다. | 개인 심화와 관계 상품의 권한이 서로 섞일 수 있어 상품별 권한 분리가 필요합니다. |
| 공유 | 부부·연인 결과는 현재 불변 `shareId` 스냅샷으로 복원됩니다. | 결과 공유의 불변성 패턴은 상품별 공유에도 재사용할 수 있습니다. |
| 부모·자녀 | 새 코칭 생성기는 컬러·카드·관계 유형·성별을 활용합니다. | 연령/발달 단계는 아직 입력·역할 판정·문장에 사용되지 않습니다. |

## 2. 관계코칭 상품 진입 구조 의견

### 2.1 세 진입 경로를 분리하는 것이 적절한가

**적절합니다.** 세 상품은 단순한 가격 차이가 아니라 관계 목적, 결과 깊이, 결과 생성기, 공유 범위가 다릅니다. 시작 화면에서 `관계 유형`을 먼저 모두 보여 주는 현재 방식보다, 먼저 **관계코칭 상품**을 선택하고 그 안에서 가능한 관계 유형을 고르게 하는 흐름이 사용자가 무엇을 구매·이용하는지 더 명확히 이해하게 합니다.

권장하는 첫 화면의 상품 카드는 아래와 같습니다.

| 상품 카드 | 가격 | 카드 안에서 선택할 관계 | 결과 범위 | 권한 |
|---|---:|---|---|---|
| **부부·연인 커플코칭** | 59,000원 | 부부, 연인 | 현재 완성된 심화 관계 분석·PDF·불변 공유 | 유료 상품 권한 필요 |
| **부모·자녀 관계코칭** | 39,000원 | 아빠-아들, 아빠-딸, 엄마-아들, 엄마-딸 | 현재 구현된 부모·자녀 전용 역할·소통·DO & DON'T 구조 | 유료 상품 권한 필요 |
| **기타 관계 무료 코칭** | 무료 | 형제자매, 친구, 직장동료 | 현재 경량 관계 결과 | 별도 결제 없음 |

이 구조에서는 `부모-자녀`라는 중간 선택값을 외부 상품 화면에 노출하지 않고, 부모·자녀 상품 안에서 곧바로 네 가지 실제 조합을 선택하게 하는 편이 자연스럽습니다.

### 2.2 공통으로 재사용할 부분과 상품별로 분리할 부분

| 구분 | 공통으로 유지할 부분 | 상품별로 분리할 부분 |
|---|---|---|
| 진입 | 두 사람 정보 입력, A→B 진행 상태, 컬러 3개 선택, 심리카드 3개 선택 | 상품 카드·가격·허용 관계 유형·안내 문구 |
| 개인 분석 | 기존 컬러 해석, 카드 해석, 컬러×심리카드 통합 분석 | 부모·자녀에서는 실제 호칭·발달 맥락을 연결하는 표현만 추가 가능 |
| 종합 분석 | A/B 결과 계산·공통 세션 형식 | 부부·연인 심화, 부모·자녀 전용 코칭, 기타 경량 결과를 각각 독립 생성기로 유지 |
| 결과·PDF | 결과 식별자, 로딩/실패 처리, 저장 구조 | PDF 제공 여부·보고서 목차·상품별 CTA |
| 공유 | 불변 결과 스냅샷, `shareId`, 공개 조회 | 공유 카드 문구·스냅샷 스키마·공개 가능한 항목 |

핵심은 `CoupleSessionData`를 없애거나 세 번 복제하지 않는 것입니다. 공통 세션에는 `productCode`를 추가하고, **결과 생성기와 권한 정책을 `productCode`로 분리**하는 방식이 가장 안전합니다.

권장하는 개념적 식별자는 다음과 같습니다.

```ts
type RelationshipProductCode =
  | "romantic_couple"   // 59,000원
  | "parent_child"      // 39,000원
  | "other_free";       // 무료
```

`relationType`은 관계 조합을, `productCode`는 가격·권한·결과 범위를 책임지게 해야 합니다. 예를 들어 `아빠-딸`은 `relationType`이고, `parent_child`는 상품 코드입니다. 이 구분이 있어야 잘못된 가격, 다른 상품 결과 화면, 잘못된 공유 스냅샷을 예방할 수 있습니다.

### 2.3 결제 → 검사 → 결과 → 공유의 권장 분리

현재의 전역 `premiumUnlocked` 방식은 상품을 둘 이상 운영하기에 적합하지 않습니다. 입금 정보 제출 직후 기기 전체를 유료로 여는 방식도, 상품별 가격·확정 상태·다른 기기 이용을 구분하기 어렵습니다.

| 단계 | 권장 책임 | 현재 구조에서 향후 보완할 점 |
|---|---|---|
| 1. 상품 선택 | 상품 코드와 가격을 고정 | 금액만으로 상품을 판별하지 않음 |
| 2. 결제 요청 | `productCode`, 가격, 결제 요청 ID를 서버에 저장 | 결제 기록에 상품 코드·권한 상태·결제 요청 ID 추가 |
| 3. 결제 확인 | 관리자가 확인하면 해당 상품의 권한 발급 | 기기 전역 `premiumUnlocked` 대신 상품별 entitlement 발급 |
| 4. 검사 시작 | 검사 세션에 `productCode`와 권한 참조를 연결 | 다른 상품 결과 생성기에 진입하지 못하도록 검사 시작 시 확인 |
| 5. 결과 저장 | 결과와 상품 코드·생성 시각·권한 참조를 연결 | 유료 결과의 재열람 및 PDF 범위 관리 가능 |
| 6. 공유 | 결과를 불변 스냅샷으로 저장하고 `shareId`만 URL에 노출 | URL에 컬러·카드·개인정보·결제정보를 넣지 않음 |

> **권장 원칙:** 결제 권한은 클라이언트 저장값만으로 판정하지 않고, 서버가 발급한 상품별 권한을 기준으로 확인합니다. 로그인이 없는 초기 단계라면 결제 확인 후 발급하는 난수형 권한 토큰을 기기에 보관할 수 있으나, 장기적으로는 계정 또는 인증된 연락처 기반의 재복원 정책을 별도로 정하는 편이 안전합니다.

공유는 구매 권한과 분리해야 합니다. 공유받은 사람은 해당 결과를 **읽기 전용**으로 볼 수 있어야 하지만, 원본 사용자의 새 검사·PDF 재발급·결제 정보에 접근해서는 안 됩니다. 지금 부부·연인에 적용한 불변 공유 스냅샷 방식은 이 원칙과 잘 맞으므로, 부모·자녀 유료 상품을 공개할 때도 별도 스냅샷 스키마로 확장하는 방식을 권장합니다.

## 3. 부모·자녀 분석에서 나이 정보의 필요성

### 3.1 나이는 유의미한가

**유의미합니다.** 컬러·심리카드는 기질과 표현 구조를 설명하는 근거이고, 연령·생활 단계는 그 기질이 부모·자녀 관계에서 어떤 상황으로 드러나는지를 해석하는 맥락입니다. 같은 ‘자기 방향을 만들어 가는 역할’도 초등 자녀에게는 작은 선택권과 과정 인정으로, 성인 자녀에게는 경계와 상호 존중으로, 부모가 고령인 가족에게는 돌봄·역할 전환을 존중하는 대화로 달라져야 합니다.

현재 부모·자녀 생성기는 역할 판정을 컬러·카드·도형에 근거해 수행하며, 나이 입력은 받지 않습니다. 기존 삶의 역할 에너지 엔진은 나이 인자를 받을 수 있지만, 역할 점수를 바꾸지는 않고 문장 속 경험 맥락만 부드럽게 조정합니다. 따라서 연령을 넣더라도 **기질 자체를 바꾸는 가중치**가 아니라 **소통·자율성·돌봄의 현실적 표현을 선택하는 맥락 변수**로 사용하는 것이 현재 철학과 가장 일관됩니다.

| 현재 섹션 | 연령/발달 단계가 바꿀 수 있는 부분 | 바꾸지 말아야 할 부분 |
|---|---|---|
| 각자의 사회적 역할 | 부모의 경험·자녀의 가능성을 말하는 생활 맥락 | 컬러·카드 기반 역할 판정 자체 |
| 우리 관계의 역할 에너지 | 보호·기준·기다림과 자율성·독립·역할 전환의 표현 강도 | 두 사람의 역할 우열 판단 |
| 자녀 기질 맞춤 소통 | 선택권의 크기, 설명 방식, 대화 시간, 존중의 방식 | 자녀를 문제행동으로 규정하는 표현 |
| DO & DON'T | 실제 대화 예문의 난이도와 경계 수준 | 고정된 훈육·진단 문구 |
| 갈등과 회복 | 갈등 후 부모가 먼저 할 수 있는 행동, 독립·돌봄의 거리 | 컬러·카드 기반 회복 방향 |

### 3.2 정확한 나이와 연령대 중 무엇이 적합한가

**권장은 ‘정확한 숫자 나이’가 아니라 ‘관계 맥락을 반영한 연령대·발달 단계 선택’입니다.** 특히 부모·자녀 코칭에서는 자녀의 만 나이보다, 자녀가 현재 어느 생활 단계에 있는지가 대화와 자율성 코칭에 더 직접적입니다. 숫자 나이는 컷오프 경계가 생기고 불필요한 개인정보를 늘리며, 같은 19세라도 재학·취업·독립 여부에 따라 맥락이 달라집니다.

권장 입력은 아래의 2단 구조입니다.

| 우선순위 | 입력 항목 | 권장 선택지 | 활용 방식 |
|---:|---|---|---|
| 1 | **자녀의 현재 생활 단계** | 영유아(0–6) / 초등(7–12) / 청소년(13–18) / 성인 초기(19–29) / 성인 자녀(30–49) / 중장년 성인 자녀(50+) | 부모의 대화 강도, 선택권, 자율성, 독립·돌봄·역할 전환 문장에 직접 활용 |
| 2 | **부모 연령대** | 30대 이하 / 40대 / 50대 / 60대 이상 | 경험·돌봄·역할 전환의 보조 문맥에만 활용 |
| 선택 | **현재 생활 관계** | 함께 거주 / 독립 생활 / 주기적 왕래 / 돌봄을 함께 논의 중 | 성인 자녀 구간에서만 선택 노출; 나이보다 실제 대화 맥락을 정교화 |

정확한 숫자 나이를 받아야 하는 요구가 생기더라도, 저장·표시에는 원 숫자를 남기지 않고 앱 안에서 위 연령대로 즉시 변환하는 방식을 권장합니다. 결과 화면에는 ‘40세’ 같은 숫자 대신 ‘성인 자녀와 서로의 생활을 존중하는 시기’처럼 맥락만 반영해야 합니다.

## 4. 단계적 도입 권장안

| 순서 | 구현 범위 | 이유 |
|---:|---|---|
| 1 | 홈에 세 상품 카드만 추가하고 각 카드가 허용 관계 유형을 가진 시작 화면으로 연결 | 사용자의 상품 이해와 진입 경로를 먼저 명확히 함 |
| 2 | `productCode`·상품별 entitlement·결제 기록의 상품 코드 분리 | 가격과 검사·결과 권한이 섞이지 않게 하는 핵심 안전장치 |
| 3 | 부모·자녀 시작 흐름에 자녀 생활 단계와 부모 연령대 입력 추가 | 이미 완성된 부모·자녀 결과에 가장 작은 범위로 맥락을 더함 |
| 4 | 부모·자녀 코칭 생성기에 발달 단계별 표현 모듈만 추가 | 컬러·카드 기반 역할 판정은 유지하면서 대화 예문을 현실화 |

## 최종 권장안
