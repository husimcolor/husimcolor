# Preview 오픈기념 행사·관리자 개별 쿠폰 검증 기록

> **범위:** 격리된 Preview DB와 Toss 테스트 런타임만 사용했다. Production DB, Production 쿠폰, 라이브 결제키, 실제 결제 승인은 변경하지 않았다.

## 대상 정책

| 항목 | 확인한 정책 |
|---|---|
| 공개 행사 | 유료 심화분석 오픈 기념 20% 할인 |
| 기간 | 2026-10-30 23:59:59 KST까지 |
| 대상 | 개인·부부/연인·부모/자녀 유료 심화분석 3종 |
| 제외 | 오프라인 코칭 |
| 로그인 | 비회원/회원 모두 사용할 수 있는 공개 행사 설계 |
| 한도 | 전체/고객별 사용 한도 없음 |
| 중복 | 주문당 쿠폰 하나만 적용 — 행사와 개별 쿠폰 중복 불가 |

## 구현 범위

- `coupons.assignedCustomerId`를 nullable로 추가했다.
  - `NULL`: 공개 행사 쿠폰
  - 값 존재: 관리자 지정 고객 전용 쿠폰
- Drizzle migration `0018_targeted_customer_coupons.sql`을 추가하고 **격리 Preview DB에만** 적용했다.
- 기존 `customers`, `coupons`, `coupon_product_rules`, `coupon_redemptions`, `admin_audit_logs` 원장만 재사용했다. 별도 고객/쿠폰 저장소를 만들지 않았다.
- 관리자 화면(기존 비밀번호/세션 방식)에 지정 이메일·대상 상품·할인 금액/비율·유효기간의 1회용 개별 쿠폰 발급 및 미사용 쿠폰 회수 UI를 추가했다.
- 고객 이메일을 입력한 뒤에도 지정 쿠폰 견적이 보이도록, 조회 전용 이메일→기존 customer 매칭을 추가했다. 이 단계는 고객 생성·쿠폰 예약·사용 이력을 만들지 않는다.

## Preview 통합 검증

| 시나리오 | 결과 |
|---|---|
| 최신 관리자 UI에서 기존 관계분석 체험권 발급 버튼 | 기존 미사용 권한의 링크 재발급 안내·URL 표시 확인. 중복 entitlement 미생성 |
| 관리자 UI의 지정 고객 쿠폰 발급 | 마스킹된 수신자·1회용 쿠폰·감사 로그 생성 확인 |
| 지정 고객 개인 심화 쿠폰 | 지정 이메일은 29,000원 → 19,000원(10,000원 할인) 견적 확인 |
| 다른 기존 Preview 고객 이메일 | `COUPON_ASSIGNED_TO_ANOTHER_CUSTOMER`로 거절 확인 |
| 지정 고객 쿠폰 취소 | 주문 `cancelled`, 쿠폰 예약 `released`, entitlement 0건 확인 |
| 오픈기념 공개 쿠폰 | 29,000원 → 23,200원, 59,000원 → 47,200원, 39,000원 → 31,200원 확인 |
| 공개 행사 한도 | Preview 행사 행은 전체/고객별 한도를 `NULL`로 설정하고, 지정 고객 ID가 없는 공개 행임을 확인 |
| 임시 QA 개별 쿠폰 | 검증 후 모두 `paused`로 회수; 활성 지정 고객 쿠폰 0건 확인 |

## 확인하지 않은 항목

- 실제 회원(Kakao 로그인) 브라우저 세션의 화면 단위 결제는 이번 검증에서 실행하지 않았다. 서버 쿠폰 규칙은 이메일로 공통 customer를 해석하므로 비회원과 회원의 체크아웃 검증 지점은 동일하지만, 실제 회원 UI 회귀는 별도 세션에서 추가 확인이 필요하다.
- 실제 날짜가 행사 종료 시점을 지난 브라우저 확인은 불가능하므로, 종료 자동 숨김은 단위 테스트와 클라이언트 정책 함수로 검증했다.
- Toss 결제 승인·실제 청구·라이브키 전환은 수행하지 않았다.
- Production 스키마 적용, 환경 변수 변경, 쿠폰 발급, 병합/배포는 수행하지 않았다.

## Production 반영 전 필수 절차

1. PR 리뷰·승인 후 별도 Production 배포를 승인한다.
2. Production에 migration을 적용하기 전 백업/적용 계획을 확인한다.
3. Production 공개 행사 행을 별도 생성한다. Preview 행사 행이나 합성 QA 데이터를 복사하지 않는다.
4. Production 쿠폰은 `assignedCustomerId=NULL`, 20%, 세 유료 분석 규칙, KST 마감, 전체/고객별 한도 없음으로 구성한다.
5. 라이브 결제 오픈 여부는 이 코드 배포와 분리하여 별도 승인·가맹점 설정·운영 QA 후 결정한다.
