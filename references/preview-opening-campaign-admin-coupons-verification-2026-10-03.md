# Preview 오픈기념 행사·관리자 개별 쿠폰 검증 기록

> **범위:** 격리된 Preview DB와 Toss 테스트 런타임만 사용했다. Production DB, Production 쿠폰, 라이브 결제키, 실제 결제 승인은 변경하지 않았다.

## 대상 정책

| 항목 | 확인한 정책 |
|---|---|
| 공개 행사 | 유료 심화분석 오픈 기념 20% 할인 |
| 기간 | 2026-10-30 23:59:59 KST까지 |
| 대상 | 개인·부부/연인·부모/자녀 유료 심화분석 3종 |
| 제외 | 오프라인 코칭 |
| 로그인 | 비회원/회원 모두 사용할 수 있는 공개 행사 설계 |
| 한도 | 전체/고객별 사용 한도 없음 |
| 중복 | 주문당 쿠폰 하나만 적용 — 행사와 개별 쿠폰 중복 불가 |

## 구현 범위

- `coupons.assignedCustomerId`를 nullable로 추가했다.
  - `NULL`: 공개 행사 쿠폰
  - 값 존재: 관리자 지정 고객 전용 쿠폰
- Drizzle migration `0018_targeted_customer_coupons.sql`을 추가하고 **격리 Preview DB에만** 적용했다.
- 기존 `customers`, `coupons`, `coupon_product_rules`, `coupon_redemptions`, `admin_audit_logs` 원장만 재사용했다. 별도 고객/쿠폰 저장소를 만들지 않았다.
- 관리자 화면(기존 비밀번호/세션 방식)에 지정 이메일·대상 상품·할인 금액/비율·유효기간의 1회용 개별 쿠폰 발급 및 미사용 쿠폰 회수 UI를 추가했다.
- 고객 이메일을 입력한 뒤에도 지정 쿠폰 견적이 보이도록, 조회 전용 이메일→기존 customer 매칭을 추가했다. 이 단계는 고객 생성·쿠폰 예약·사용 이력을 만들지 않는다.

## 2026-10-04 Preview 결제·관계 리포트 통합 검증

> 아래 검증은 **격리 Preview DB와 Toss 테스트키**에서만 수행했다. 실청구·라이브키·Production 주문/고객/이용권/쿠폰은 만들거나 변경하지 않았다.

| 시나리오 | 확인 결과 |
|---|---|
| 일반 부부·연인 상품 진입 | Preview 일반 CTA가 심사용 review-only로 가지 않고, 지속형 테스트 결제 checkout으로 진입하도록 수정·배포 |
| 공개 행사 적용 | 비회원 테스트 checkout에서 59,000원 → 할인 11,800원 → **47,200원** 표시 및 Toss 테스트 승인 확인 |
| 결제 원장 | 테스트 주문 `paid`, 결제 승인, 행사 쿠폰 `consumed`, 관계상품 entitlement **1건** 확인 |
| 기존 검사 순서 | A/B 모두 기본 정보 저장 → 컬러 3개 → 컬러 해석 → 비공개 심리카드 → 카드 해석 → 최종 제출 흐름 유지 확인 |
| A/B 결과 접근 | 두 참여자 모두 제출 후 같은 통합해석 화면과 PDF 리포트 다운로드 화면 진입 확인; 완료 링크 재접속 시 검사 시작 화면으로 돌아가지 않음 |
| PDF 중복 방지 | 관계 세션 기준 생성 PDF **1건**, 상태 `generated` 확인 |
| 이메일 처리 | 결제자 A용 PDF outbox **1건**, 상태 `sent`, 시도 횟수 **1회**, 관계 세션 `completed` 전이 확인 |
| 이메일 수신 범위 | B의 이메일 입력·발송 없이 결과/PDF 접근을 유지. A 메일함의 실제 수신 열람은 개인정보 보호상 별도 사용자 확인 항목 |
| 기존 완료 세션 복구 | 이메일 대기 상태에서도 A/B 결과 접근을 허용하고, Preview 관리자만 새 A/B 접근 토큰을 발급하도록 보완. 답변·결과·PDF·outbox는 보존하고 기존 링크만 무효화하며 감사 로그를 남김 |

### 이메일 대기 상태 수정

- 직접 원인: PDF 생성 후 `email_pending` 상태의 세션을 화면과 결과 API가 `completed`로만 제한해, A/B 결과 접근과 outbox 발송 재개가 분리되어 있었다.
- 조치: `email_pending`에서도 결과/PDF를 제공하고, A의 Preview 결과 화면 진입 시에도 동일 outbox 발송을 1회 재개하도록 보완했다.
- 중복 방지: DB outbox claim lock, outbox ID 기반 공급자 idempotency key, 관계 세션 이메일 완료 전이 조건을 함께 사용한다.
- 이 세션에서 결과 접근 링크는 복구 과정상 여러 번 재발급되었으나, 이는 접근 토큰 교체 감사 기록일 뿐 PDF·outbox·이용권을 새로 만들지 않았다.

## 확인하지 않은 항목

- 실제 회원(Kakao 로그인) 브라우저 세션의 화면 단위 결제는 이번 검증에서 실행하지 않았다. 서버 쿠폰 규칙은 이메일로 공통 customer를 해석하므로 비회원과 회원의 체크아웃 검증 지점은 동일하지만, 실제 회원 UI 회귀는 별도 세션에서 추가 확인이 필요하다.
- 실제 날짜가 행사 종료 시점을 지난 브라우저 확인은 불가능하므로, 종료 자동 숨김은 단위 테스트와 클라이언트 정책 함수로 검증했다.
- Toss 테스트 결제 승인과 Preview 원장은 검증했지만, 라이브키 전환·실제 청구는 수행하지 않았다.
- 새 세션에서 B 최종 제출 직후의 즉시 발송 경로는 이번 기존 세션 복구와 별개로 반복하지 않았다. 결과 화면 재진입 fallback으로 실제 outbox `sent` 전이는 검증했다.
- Production 스키마 적용, 환경 변수 변경, 쿠폰 발급, 병합/배포는 수행하지 않았다.

## Production 반영 전 필수 절차

1. PR 리뷰·승인 후 별도 Production 배포를 승인한다.
2. Production에 migration을 적용하기 전 백업/적용 계획을 확인한다.
3. Production 공개 행사 행을 별도 생성한다. Preview 행사 행이나 합성 QA 데이터를 복사하지 않는다.
4. Production 쿠폰은 `assignedCustomerId=NULL`, 20%, 세 유료 분석 규칙, KST 마감, 전체/고객별 한도 없음으로 구성한다.
5. 라이브 결제 오픈 여부는 이 코드 배포와 분리하여 별도 승인·가맹점 설정·운영 QA 후 결정한다.
