# 관계 코칭 검사 — 각자 휴대폰 초대 링크 구현 계획

작성일: 2026-09-30
적용 범위: **결제 후 사용하는 유료 관계 심화분석**의 추가 검사 경로
보호 범위: 기존 한 휴대폰 검사, 무료 친구 관계 분석, 개인 심화분석, 분석 문구/계산, 결과 UI 구조, PDF 본문, Kakao 불변 공유 스냅샷, 공개 유료 차단 정책

## 1. 현재 구조 확인 결과

현재 관계 검사는 `@couple_session` 한 개를 기기 로컬 `AsyncStorage`에 보관합니다. 첫 번째 사람이 컬러·심리카드 선택을 마치면 같은 기기에서 두 번째 사람 선택으로 넘어가며, 두 데이터가 갖춰지면 `couple-result`이 로컬 데이터를 기반으로 기존 분석 함수를 실행합니다.

따라서 이 로컬 세션을 다른 휴대폰과 공유하면 다음 문제가 생깁니다.

- 상대방 휴대폰에는 결제자의 `AsyncStorage`와 entitlement 시작 표식이 없습니다.
- 현재 완료 판정은 브라우저 화면 전환일 뿐 서버의 두 참여자 상태가 아닙니다.
- 결과/PDF/메일 중복 방지를 위한 세션 단위 잠금이 없습니다.

기존 경로를 바꾸지 않고 별도 서버 세션 경로를 추가해야 합니다.

## 2. 확정 아키텍처

### 2.1 검사 방식

| 방식 | 적용 | 기존/신규 | 데이터 위치 |
|---|---|---|---|
| 한 휴대폰에서 함께 검사하기 | 기존 모든 관계 검사 | **기존 경로 유지** | 기존 `@couple_session` |
| 각자 휴대폰에서 검사하기 | entitlement가 확인된 유료 관계 심화분석 | **신규 경로** | 서버 관계 세션 + 참여자별 암호화 답변 |

무료 친구 관계 분석은 현재 동작을 유지하며, 결제 없이 상대에게 검사 권한을 넘기는 초대 링크 경로를 추가하지 않습니다.

### 2.2 관계 세션과 토큰

결제 entitlement를 소비해 `analysis_runs`를 생성한 직후, 별도 `relationship_sessions`를 한 번 생성합니다.

- 한 주문/분석 실행은 하나의 관계 세션에만 연결됩니다. (`analysisRunId` unique)
- A(결제자)와 B(초대받은 상대) 슬롯은 `relationship_participants`의 `(sessionId, participant)` unique 제약으로 고정합니다.
- 초대 URL에는 UUID/순번 대신 `crypto.randomBytes(32).toString("base64url")` 형식의 고엔트로피 토큰만 포함합니다.
- DB에는 원문 토큰을 저장하지 않고 서버 비밀 HMAC 해시만 보관합니다.
- A의 검사 접근 토큰, B의 초대 토큰, 완료 후 결과 조회 토큰을 서로 분리합니다.
- 초대 토큰은 최종 완료 전까지 재사용할 수 있으며, 완료 후에는 어떤 검사 조회·저장·제출 권한도 주지 않습니다.

### 2.3 저장 구조

`relationship_sessions`

- 주문/entitlement/analysis run/product/relation type 연결
- 모드(`one_device` / `invite_link`)와 상태
- A 접근·B 초대·결과 조회용 토큰 HMAC
- 리포트 생성·이메일 전달·완료 시각과 오류 코드
- 상태: `collecting` → `awaiting_partner` → `report_generating` → `email_pending` → `completed`

`relationship_participants`

- A/B 슬롯, 진행 상태(`not_started` / `in_progress` / `submitted`)
- 검사 참여 확인 시각·버전
- 자동 저장 초안 및 최종 제출본(모두 AES-256-GCM 암호화)
- 초안 revision, 시작/최종 제출 시각

답변에는 기존과 같은 성별·종교·선택 컬러·선택 심리카드와 함께 **검사자가 직접 선택한 실제 관계 역할**을 저장합니다. 분석 문구·공식·PDF 구조는 새로 만들거나 변경하지 않습니다.

### 2.4 실제 관계 역할과 짝 검증

- 부부는 `남편 ↔ 아내`, 연인은 `남자친구 ↔ 여자친구`만 허용합니다.
- 부모·자녀는 `아빠/엄마 ↔ 아들/딸`만 허용하며, 딸이 결제자(A)이고 엄마가 초대 상대(B)여도 역할을 기준으로 `엄마-딸` 분석으로 확정합니다.
- 역할은 성별 선택과 일치해야 하며, 상대가 먼저 선택한 역할은 초대 화면에서 공개되는 **역할값만** 사용해 가능한 짝으로 제한합니다. 컬러·카드·종교 등 상대 답변은 노출하지 않습니다.
- UI를 우회한 불일치 제출도 서버 트랜잭션에서 `RELATIONSHIP_ROLE_PAIR_INVALID`으로 거부하고, 참가자 제출·리포트·이메일 상태를 변경하지 않습니다.
- 각자 휴대폰 초대 경로의 결과/PDF에는 실제 역할을 우선 표기합니다. 기존 한 휴대폰 검사와 기존 PDF는 기존 호칭을 유지합니다.

## 3. 서버 상태 전이와 중복 방지

1. A가 검사 방식에서 **각자 휴대폰**을 선택하면, entitlement 소비와 관계 세션 생성을 단일 서버 트랜잭션으로 처리합니다.
2. A/B는 각자의 정보 입력, 컬러 3개, 심리카드 3개를 단계별로 저장합니다. 저장은 덮어쓰기가 아니라 revision을 증가시키며, 재접속 시 마지막 암호화 초안을 복원합니다.
3. B가 최종 제출해도 A가 미완료이면 `awaiting_partner`만 반환하고 리포트를 만들지 않습니다. A가 먼저 완료한 경우도 동일합니다.
4. 두 슬롯의 `submitted`가 확인된 요청 하나만 compare-and-set 방식으로 `report_generating`을 선점합니다. 동시 제출, 중복 클릭, 새로고침에서 후속 요청은 진행 중/완료 상태를 반환하며 리포트를 다시 만들지 않습니다.
5. 서버는 기존 관계 분석 계산과 기존 PDF 생성기를 재사용하여 private PDF/outbox를 한 번만 적재합니다. `private_documents`의 `(analysisRunId, documentType)`와 `email_outbox`의 문서별 unique 제약도 함께 중복을 막습니다.
6. 이메일 outbox가 `sent`가 되었을 때만 해당 관계 세션을 `completed`로 변경합니다. 실패/재시도 대기에는 `email_pending`으로 유지합니다.
7. `completed` 이후 B 초대 링크는 전용 완료 안내만 반환하고, 초안·최종 답변 저장·재제출을 모두 거부합니다. 결과 조회는 별도의 결과 토큰 경로에서만 허용합니다.

## 4. 화면 흐름

### 결제자(A)

1. 기존 관계 유형/결제 흐름을 통과
2. **검사 방식 선택**: `한 휴대폰에서 함께 검사하기` 또는 `각자 휴대폰에서 검사하기`
3. 각자 휴대폰 선택 시 A 정보 입력 → A 컬러/카드 검사
4. A 완료 후 초대 링크 공유(시스템 공유·복사) 및 상대 대기 화면
5. B 제출 후 상태 자동 조회 → 서버 완료 시 기존 `couple-result` 화면을 별도 결과 조회 권한으로 표시

### 초대받은 상대(B)

1. `relationship-invite?token=...` 접근
2. 링크 유효성 확인과 검사 참여 확인 문구 표시
3. B 정보 입력 → B 컬러/카드 검사
4. 각 단계 자동 저장, 동일 링크 재접속 시 이어하기
5. 최종 제출 후 A 완료 여부에 따라 `상대방 검사 대기 중` 또는 완료 안내

기존 한 휴대폰 경로의 버튼·화면 이동·로컬 세션 데이터는 변경하지 않습니다.

## 5. PDF·이메일과 결과 권한

- 서버 전용 서비스가 기존 `createCouplePdfBuffer`/`createParentChildPdfBuffer`, private storage, `email_outbox`, Resend delivery 경로를 사용합니다.
- 신규 결과 세션은 결과 PDF 이메일을 정확히 한 번만 큐잉합니다.
- 완료된 초대 URL은 결과 권한이 아니며, 검사 화면으로 진입하거나 데이터를 수정할 수 없습니다.
- 결과 화면은 A가 가진 별도 고엔트로피 결과 조회 토큰으로만 읽습니다. B 초대 토큰으로는 결과 원문을 반환하지 않습니다.
- Production의 Resend/cron E2E 준비 상태와 유료 공개 gate는 이번 작업의 범위를 넘어 유지됩니다. 유료 공개 gate는 계속 `false`입니다.

## 6. 검수 항목

자동테스트로 다음을 검증합니다.

1. 기존 한 휴대폰 경로가 별도 코드로 유지되고, 친구 무료 경로가 변하지 않음
2. 세션별 A/B 고정 연결과 추측 불가능한 토큰 원문 비저장
3. 단계별 draft 저장/재접속/최종 제출 후 수정 거부
4. 한 사람 완료 시 결과 생성 없음, 양측 완료 시 한 번만 생성
5. 동시 제출·반복 제출에서 한 요청만 report generation 선점
6. 완료된 링크 재접속 시 검사 권한 거부 및 완료 안내
7. 결과 토큰과 초대 토큰의 권한 분리
8. email outbox가 sent가 된 경우에만 세션 `completed` 전이
9. TypeScript, 전체 Vitest, 기존 PDF/공유/entitlement 회귀 검수
10. 부부·연인 및 부모·자녀 실제 역할 선택, 검사 순서와 무관한 역할 확정, 불일치 역할 제출 거부

## 7. 변경 원칙

- 기존 관계 분석 결과 내용, PDF 본문/구조, Kakao `shareId` snapshot은 수정하지 않습니다.
- 기존 화면은 신규 파라미터를 받는 경우에만 서버 결과 세션을 읽고, 기존 로컬 흐름은 그대로 유지합니다.
- Toss 실결제, 공개 유료 판매, DNS, 비밀값은 변경하지 않습니다.
